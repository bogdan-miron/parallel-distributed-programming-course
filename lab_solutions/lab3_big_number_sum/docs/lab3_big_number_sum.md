## Requirements

The program adds two big numbers (more than 10 digits) with MPI, in C++. A number is an array of digits with the least significant digit at position 0. The numbers are read from `Numar1.txt` and `Numar2.txt` (the number of digits, then the digits) and the sum is written to `Numar3.txt`. The statement asks for a sequential version (variant 0) and these MPI versions: variant 1 with standard send and receive, which has to be correct even if send does not use buffers, variant 2 with scatter and gather where process 0 adds too, variant 3 with non-blocking communication, and as a bonus variant 1.1, the addition that starts before the carry arrives. For all of them the time includes reading the numbers, and the output has to be the same as the sequential one on every run.

## Design

The files have the number of digits on the first line and the digits on the second, written in the order of the array, so the least significant digit comes first. The statement does not say which end of the number is written first. I chose this order because process 0 has to send the first digits to process 1 before it reads the rest, and those are the digits that have no carry coming in. `Numar3.txt` has only the digits of the sum, in the same order, and the sum has one digit more than the longer number when a carry is left. If a number is shorter it is padded with zeros while it is read.

Variant 1. Process 0 only reads, sends, receives and writes. The other p - 1 processes add. Process 0 first sends the number of digits n of the longer number to everyone (`MPI_Bcast`). The digits are split between the p - 1 processes so that each one gets n / (p - 1) digits and the first n % (p - 1) get one more, so every digit is added exactly once. Process 0 reads one piece from each file and sends it to process 1, then the next piece to process 2, and so on, so it never holds the whole number. A process with id > 0 first receives its two pieces and then the carry from the previous process (process 1 uses 0), adds, sends the carry to the next process and then sends the digits of the sum to process 0. The carry is sent before the sum on purpose, so the next process does not wait for the sum to reach process 0. After sending all the pieces process 0 receives the sums in the order of the processes and writes each one as soon as it arrives. The last process also sends the final carry after its digits, and process 0 writes it as one more digit if it is 1.

I checked that there is no deadlock by assuming that `MPI_Send` waits for the receiver: process 0 sends to process 1, 2, ... in order and each of them starts with the receive from process 0. The carry goes only forward, from process i to i + 1, and the process i + 1 receives it after its pieces. The sums go to process 0, which receives them after it sent everything. There is no cycle of processes waiting for each other. To test it I built the program a second time with `MPI_Ssend` instead of `MPI_Send` (`-DSYNC` in the Makefile) and ran it the same way. Variant 1 with `MPI_Ssend` is called 1s in the results.

Variant 1.1. The question in the statement is whether a process can add before the carry arrives. It can. Each process adds its digits as if the carry was 0 and keeps the result. When the real carry arrives, if it is 1, the process adds 1 to its sum, starting at the lowest digit and going up while the digits are 9, so in most cases it changes one digit. What this variant needs is to know the carry that goes out of the process, which the next one waits for. If the sum of the piece is not 99...9, the carry that goes out is the one computed with carry 0, whatever comes in, so the process sends it right away, before it receives its own carry. Only when the sum is 99...9 does the carry that goes out depend on the carry that comes in (it is the same), so that process has to wait for it. The numbers `9999 4444 4444 9999` and `9999 5555 5555 9999` from the statement are a case where the middle pieces are 99...9 and the carry has to go through them. I implemented this one and compared it with variant 1.

Variant 2. Process 0 reads both numbers completely. If p does not divide n, n is rounded up to a multiple of p and the numbers are padded with zeros. `MPI_Scatter` gives each process, including process 0, n / p digits of each number. Each process receives the carry from the previous one (process 0 starts with 0), adds, and sends the carry to the next one. `MPI_Gather` brings the digits of the sum to process 0, which writes the file. The carry that goes out of the last process is sent to process 0 after the gather (not before: with a synchronous send the last process would wait for process 0, while process 0 waits in the gather for it, and the program blocks, which `MPI_Ssend` shows). If n was rounded up, the final carry is already the digit at position n.

Variant 3. Process 0 reads a piece for each process and sends it with `MPI_Isend`, keeping the buffers until all the sends are done. A process with id > 1 receives the two pieces from process 0 and the carry from the previous process, and the order in which they arrive is not known, so it starts the three receives with `MPI_Irecv` and waits for all of them with `MPI_Waitall`. Then it adds and sends the carry and its sum with `MPI_Isend`. Process 0 starts one `MPI_Irecv` for each sum, directly into its place in the result array, and waits for all with `MPI_Waitall`, so it does not matter in which order the processes finish. The statement says N / p digits for variant 3 and N / (p - 1) for variant 1. Process 0 does not add in either of them, so only p - 1 processes get digits, and I used N / (p - 1) in both.

## Implementation

Everything is in `mpi/main.cpp`, compiled with `mpic++ -std=c++17 -O2`, and started with `mpirun -np p build/main <variant>`, where the variant is 0, 1, 1.1, 2 or 3. The sequential version needs one process. It writes `output_seq.txt`. The parallel ones write `Numar3.txt` and process 0 compares it with `output_seq.txt` in `sameFile()` after the time was taken, on every run. If the files are different the program exits with code 1.

The functions are `readDigits()` (reads a piece of a number, zeros after the last digit), `addDigits()` (adds two pieces and a carry), `chunkSize()` and `chunkStart()` (the split with the remainder), `sequential()`, `master1()` with `worker1()` and `worker11()` for variants 1 and 1.1, `variant2()`, and `master3()` with `worker3()`.

The time is taken by process 0 with `MPI_Wtime()`, after a barrier that starts all the processes together and before a barrier at the end. It starts before the files are opened and ends after the sum is written, so it includes reading the numbers, as the statement asks, and writing the result. The same is measured in the sequential version. The time in ms is the only line printed. `tools/bench.sh` runs the program 10 times, each run being a new `mpirun`, and saves the mean in a csv.

## Tests

I used the tests from the statement. For variants 1, 1.1 and 3: the 16 digit numbers with 5 processes, 10000 and 10000 digits and 100 and 100000 digits with 5, 9 and 17 processes. For variant 2: the 16 digit numbers with 4 processes, 1000 and 1000 digits and 100 and 100000 digits with 4, 8 and 16 processes. Variant 1 was also run with `MPI_Ssend` for the same cases. The digits are random and made once by `scripts/gen_data.py`, so all the runs of a test use the same files. Machine: {{machine}}. The number of processes is bigger than the number of cores in some tests, so I started `mpirun` with `--oversubscribe`.

`scripts/gen_data.py` also computes the sum with Python integers and writes it in `expected.txt`. In the demo I compared the result of the sequential version with it, so the reference for all the other runs is not only my own program. The demo also adds 99...9 (40 digits) and 1, where the carry has to go through all the processes, with 3, 5 and 9 processes, for the variants 1 with `MPI_Ssend`, 1.1 and 3, and with 4 and 8 processes for variant 2.

## Results and analysis

{{table:mpi}}

Every MPI version was slower than the sequential one in every test. The speedups are between 0.01 and 0.24, so even the best case took about four times as long as the sequential program. The best result of each test was variant 2 with 4 processes for the 16 digit numbers (0.12) and for 1000 digits (0.06), and variant 3 with 5 processes for 10000 digits (0.24) and for 100 and 100000 digits (0.14).

The time depends on the number of processes much more than on the size of the numbers. Variant 1 with 5 processes took 15.94 ms for 16 digits, 27.53 ms for 10000 digits and 23.05 ms for 100 and 100000 digits, while the sequential program took 1.02, 4.54 and 2.43 ms. With only 16 digits the parallel versions still needed between 8.64 and 37.26 ms, so most of the time is not the addition. For variant 1 on 10000 digits the time went from 27.53 ms with 5 processes to 42.82 ms with 9 and 84.06 ms with 17, about 5 ms for each process, and the time grew with the number of processes in the same way for variants 1s, 1.1, 2 and 3 in every test. I think this is the cost of the communication between the processes and of the carry going along the chain, and not the cost of adding the digits, because the whole sequential program, with reading and writing the files, took 2.43 ms for 100 and 100000 digits. I did not measure the parts separately, so this is a guess. With 17 processes there are also more processes than the 16 logical cores of the machine.

The runs of the same test differ a lot. Variant 2 with 4 processes had a mean of 11.98 ms on 1000 digits, with a minimum of 0.18 ms and a maximum of 30.18 ms, and a mean of 8.64 ms on 16 digits, with a minimum of 0.20 ms. In those fastest runs the parallel program was faster than the mean sequential time of the test (0.71 and 1.02 ms), but the mean is dominated by the slow runs, and the mean is what the table shows.

Variant 1 and variant 1s (`MPI_Send` and `MPI_Ssend`). Variant 1s was slower than variant 1 in all 7 tests, by 1% to 134%: 37.26 against 15.94 ms for 16 digits, 27.84 against 27.53, 49.16 against 42.82 and 102.52 against 84.06 ms for 10000 digits, and 29.59 against 23.05, 52.23 against 46.32 and 99.17 against 90.86 ms for 100 and 100000 digits. `MPI_Ssend` returns only after the receiver started the receive, while `MPI_Send` can return after the message is copied to a buffer, which is probably the reason. The 10 runs of a test vary a lot (the 1s runs with 16 digits went from 18.26 to 65.49 ms), so only the 16 digit test shows a big difference. Variant 1s passed the check on every run, so variant 1 does not depend on the send being buffered.

Variant 1.1 against variant 1. Variant 1.1 was faster in 3 of the 7 tests (10000 digits with 5 and 9 processes, 21.65 against 27.53 ms and 35.79 against 42.82 ms, and 100 and 100000 digits with 9 processes, 44.23 against 46.32 ms), the same in one (23.10 against 23.05 ms, 100 and 100000 digits, 5 processes) and slower in 3 (16 digits, 23.81 against 15.94 ms, and 17 processes, 106.99 against 84.06 ms and 94.93 against 90.86 ms). I could not see a gain from starting the addition before the carry. The addition of a piece is a very small part of the time, so doing it earlier saves almost nothing, and the carry still goes through the processes one after the other. In the 16 digit test two of the pieces of the sum are 9999, so those processes also had to wait for the carry before they could send theirs on.

Variant 2 against variant 3. In the test with 100 and 100000 digits variant 3 was faster than variant 2 with every number of processes: 17.83 ms with 5 processes against 30.23 ms for variant 2 with 4, 34.52 against 49.47 ms with 9 against 8, and 52.17 against 101.81 ms with 17 against 16 (the statement uses different numbers of processes for the two). Probably it is because in variant 3 the receives do not wait for any order, while in variant 2 the gather waits for the slowest process and process 0 also has to wait for the carry. In the 16 digit test variant 2 was faster (8.64 against 15.48 ms), but these two have different numbers of processes and the numbers are very small. Variant 3 was also the fastest of variants 1, 1s, 1.1 and 3 in all the tests, by a small margin for 16 digits (15.48 against 15.94 ms for variant 1).

To get a speedup with this problem the numbers would probably have to be much bigger, or the messages much cheaper, because the carry makes the additions depend on each other. I did not try bigger numbers.
